<details>
<summary align="center"><b>📖 &nbsp;More About My Journey</b></summary>
<br/>

<div align="center">

I started out simply curious about how websites worked, and that curiosity slowly
turned into a genuine craft. Somewhere between debugging my first broken layout
and shipping my first working feature, I realized that building software is as
much about **discipline** as it is about **creativity**.

Today, as a BCA student, I split my time between coursework, personal builds,
and diving deep into how artificial intelligence is reshaping the way we build
software. I'm drawn to systems that feel effortless to use — the kind of
products where the complexity is hidden and only the clarity remains.

I believe the best interfaces don't shout for attention. They earn trust
through consistency, restraint, and care in the smallest details.

</div>

</details>

<br/>

<details>
<summary align="center"><b>🎨 &nbsp;My Design Values</b></summary>
<br/>

<div align="center">

| Value | Meaning |
|:--:|:--|
| **Clarity** | Every screen should explain itself without instructions |
| **Restraint** | Say more with less — remove until it breaks, then add back one thing |
| **Consistency** | Spacing, color, and type should feel like a single decision, repeated |
| **Performance** | Beautiful only counts if it's fast |
| **Accessibility** | Premium design should never exclude anyone |

</div>

</details>

<br/>

<details>
<summary align="center"><b>🧭 &nbsp;How I Approach Problems</b></summary>
<br/>

<div align="center">

```
1. Understand the real problem, not just the reported symptom
2. Sketch the simplest possible solution before reaching for tools
3. Build the smallest working version first
4. Refine relentlessly — structure, then style, then polish
5. Ship, observe, and iterate with intention
```

</div>

</details>

## 𝟭𝟱 &nbsp;·&nbsp; HOW I WORK

</div>

<br/>

<table align="center" width="85%">
<tr>
<td width="50%" valign="top">

**🌱 Before Writing Code**

- Understand the actual problem, not the assumed one
- Sketch the flow before touching a keyboard
- Decide what the interface should *not* include

</td>
<td width="50%" valign="top">

**⚙️ While Building**

- Small, atomic commits with clear messages
- Refactor early, refactor often
- Test the unhappy paths, not just the happy ones

</td>
</tr>
<tr>
<td width="50%" valign="top">

**🧪 Before Shipping**

- Re-read the code as if someone else wrote it
- Check spacing, contrast, and responsiveness
- Remove anything that doesn't earn its place

</td>
<td width="50%" valign="top">

**📈 After Shipping**

- Reflect on what could be simpler next time
- Document decisions for future-me
- Move on to the next problem with a clear head

</td>
</tr>
</table>

## 𝟭𝟲 &nbsp;·&nbsp; DESIGN PRINCIPLES I FOLLOW

</div>

<br/>

<div align="center">

| Principle | In Practice |
|:--:|:--|
| **Whitespace is a feature** | I let sections breathe instead of packing them tight |
| **Hierarchy over decoration** | Size, weight, and color guide attention — not extra elements |
| **Motion with purpose** | Animation should clarify, never distract |
| **One accent, used well** | A single highlight color says more than five competing ones |
| **Content-first layout** | Structure emerges from the content, not the other way around |
